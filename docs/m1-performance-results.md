# M1/T1 performance evidence

Measured 2026-11-03 with Node.js, CPU details omitted, platform details omitted. The candidate is
T1, generated from [compiler/compiler.mini](../compiler/compiler.mini) by T0.
Both compilers emitted identical bytes for every measured workload and
application, so runtime differences below reflect host noise, not different
generated programs.

The raw reports are [runtime evidence](m1-runtime-baseline.json),
[application evidence](m1-application-baseline.json), and
[self-build evidence](m1-self-build.json).

## Verification

- `mini test`: 258/258 active scenarios passed; four proposals remain pending.
- `node tools/candidate.ts .cache/compiler.mini.ts`: 224/224 Mini-source
  scenarios passed; four cases pending; nine tool cases skipped.
- `node tools/application-performance.ts --check .cache/compiler.mini.ts`:
  69/69 application/fixture combinations passed.
- A local differential pass compiled all 180 `.mini` files under `cases/`,
  `samples/`, and `compiler/` with T0 and T1 and compared stdout, stderr, exit
  status, generated bytes, and token JSON. All 180 compile results and all 180
  token streams matched.

The four earlier `tooling.release` failures were a test-harness cleanup race,
not a compiler difference: Node's recursive removal intermittently reported
`ENOTEMPTY` for a copied Git worktree. Retrying that removal fixed all twelve
release scenarios and the complete suite.

## Synthetic compiler workloads

The [runtime audit](runtime-performance.md) ran twice with the same source,
harness, and generated output. Generated workload medians stayed within ordinary
run noise (roughly 0.8–1.1x); the identical generated hash confirms no code
difference. Execution medians for the complete-compiler probes were 1.01–1.09x,
again with identical emitted bytes.

Fresh-process compile medians, T0 to T1:

- 1,000 statements: 69.1 to 73.7 ms (1.07x).
- 4,000 statements: 73.2 to 96.1 ms (1.31x).
- 16,000 statements: 91.0 to 156.8 ms (1.72x).
- 10,000-character text literal: 64.5 to 69.9 ms (1.08x).
- 40,000-character text literal: 63.5 to 76.0 ms (1.20x).
- 160,000-character text literal: 64.6 to 76.4 ms (1.18x).
- 100-term addition expression: 65.7 to 65.0 ms (0.99x).

The 1,000- and 4,000-term expression probes still hit Node's `.ts` stack limit
under both compilers; the emitted text is identical, and the flat TS and `.mjs`
controls run. This is the existing [emitted-expression depth issue](runtime-performance.md#separate-expression-stress-finding),
not an M1 regression.

## Self-build

`compiler/compiler.mini` is 43,897 bytes. In a 21-sample alternating A/B run,
T1 changed self-build wall time from 74.3 to 79.8 ms (1.075x). User CPU rose
from 0.10 to 0.13 s, maximum RSS from 90.1 to 94.6 MiB (1.05x), and peak
footprint from 46.9 to 52.4 MiB (1.115x). Output was byte-identical.

The full generation chain was stable and identical:

- Generation 1: 80.8 ms, 90.7 MiB RSS, 47.6 MiB footprint.
- Generation 2: 81.9 ms, 93.6 MiB RSS, 51.5 MiB footprint.
- Generation 3: 81.8 ms, 94.9 MiB RSS, 52.7 MiB footprint.

Wall-time variance across repeated runs was larger than the T0/T1 difference;
the consistent signals are higher T1 user CPU and about 5% higher self-build RSS.

On a 304,071-byte, 16,000-assignment source, T1 took 147.6 ms versus 91.1 ms
(1.62x), with user CPU 1.69x. Peak RSS and footprint were lower for T1 on this
input (about 0.95x and 0.93x). The runtime audit's separate probe measured 1.72x
on the same size, so the compile-time regression is real and grows with source
size.

## Paired applications

The full [application suite](application-performance.md) ran once with T0 and
once with T1. Both verified 46 semantic fixture checks and 690 measured calls.
All ten generated applications were byte-identical between compilers.

T0-to-T1 compilation wall time for the assembled applications:

- Word frequencies (1,651 bytes): 70.3 to 66.9 ms (0.95x).
- Log summary (2,515 bytes): 63.5 to 70.5 ms (1.11x).
- CSV cleanup (1,865 bytes): 63.6 to 68.7 ms (1.08x).
- Configuration parsing (2,866 bytes): 64.4 to 61.3 ms (0.95x).
- Dependency traversal (2,976 bytes): 62.9 to 61.5 ms (0.98x).
- Template rendering (2,471 bytes): 63.1 to 60.7 ms (0.96x).
- Expression evaluation (3,997 bytes): 63.6 to 62.9 ms (0.99x).
- Tokenization (8,284 bytes): 67.5 to 70.5 ms (1.04x).
- Source indexing (8,917 bytes): 66.4 to 73.5 ms (1.11x).
- Compiler pipeline (15,279 bytes): 59.8 to 76.3 ms (1.28x).

At the largest input, generated Mini applications took 0.94–1.33x matched
handwritten TS warm wall time. The actual-T0 references remained faster:
tokenization 6.49x, source indexing 5.35x, and compiler pipeline 3.61x warm
wall time. These are language/runtime representation costs already documented
for the subset, not new T1 output differences.

## Profiling and interpretation

A CPU profile of the 16,000-statement compile put T1's largest self-time entries
in `tokenize`, `is_letter`, `parser_statement`, `new_token`, `$mini_text_get`,
`lex_advance`, `parser_new`, and `expression_new`. T0's corresponding profile was
dominated by its `tokenize`, parser construction, and statement parsing.

This matches the expected port shape: tokens and expressions are maps, each
token is allocated field by field, parser state is accessed through map helpers,
and character classes use text membership. The candidate does not change
generated program performance; it spends more compiler time on large inputs.

## Promotion status

T1 is functionally equivalent on the complete current corpus and the ordinary
example. Self-build wall time is within a few percent with about 5% higher RSS;
large synthetic sources remain materially slower to compile (about 1.6–1.7x at
16,000 statements). That is a performance gate, not a correctness gate.

Optimize only with evidence and preserve the fixed point. The first candidates
are token/expression map allocation, character membership helpers, and repeated
parser-state lookups. T0 stays active until the promotion criteria in
[self-hosting readiness](self-hosting-requirements.md) are accepted.
