# Releases

Release builds are generated by CI from annotated tags. Tags identify source
commits; a release adds built artifacts, notes, and checksums.

## Official cycle

1. Choose the next group or product versions in
   [config/versions.json](../config/versions.json).
2. Update [versioning](versioning.md), [CHANGELOG](../CHANGELOG.md), and any
   product-specific version files.
3. From a clean checkout, run the build and gates:

   ```text
   ./bin/bootstrap
   ./bin/mini check
   ./bin/mini test
   ./bin/mini test --unit
   ```

4. Commit the version preparation.
5. Create one annotated tag at that commit:

   ```text
   git tag -a mini-v0.5.0-v0.2.0-alpha.4 -m "mini 0.5.0 alpha.3"
   ```

   Tag names use `product-vGROUP-vPRODUCT`. The language product is `lang`, not
   `language`.
6. Push the branch, then the tag:

   ```text
   git push github main
   git push github mini-v0.5.0-v0.2.0-alpha.4
   ```

The tag push starts:

```text
CI
 → package
 → upload draft assets
 → publish
```

The release workflow refuses dirty checkouts, lightweight tags, mismatched
registry versions, and tags that are not at the pushed commit.

## Artifacts

A release build produces:

```text
minilang-TAG.tar.gz
manifest.json
RELEASE-NOTES.md
SHA256SUMS
```

VS Code releases additionally include:

```text
mini-GROUP-vPRODUCT.vsix
```

The source archive includes the tracked bootstrap seed and is bootstrapped during
packaging. Generated tools and launchers are built from
[bin/bootstrap](../bin/bootstrap), not copied from stale files.

`manifest.json` and the packaged `RELEASE.json` record the full source commit.
Release notes link the full source commit and bold its 12-character prefix. CI
artifact names include the short source revision.

## Snapshots

Every CI run builds an extracted snapshot distribution and uploads it as a
workflow artifact. A local snapshot can be built with:

```text
./bin/mini release dist/release
```

Snapshots are never published as GitHub releases.

The Release workflow also supports manual `workflow_dispatch` runs. Those build
and upload artifacts without publishing.

## VS Code

VS Code releases use the independent `vscode-v*` stream. The workflow installs
the locked VS Code packaging dependencies when the triggering tag is
`vscode-v*`, builds the extension from the committed source archive, and adds the
VSIX to the release assets.

## Showcase

The [Pages workflow](../.github/workflows/pages.yml) builds `site/` and deploys
`dist/site/`. Enable Pages with **GitHub Actions** as the source before the first
deployment. The workflow skips repository pushes while the repository is private
and stays available through manual dispatch. See the [site notes](../site/README.md)
for the local preview and publication steps.

## Product tags

Product tags are independent:

```text
mini lang compiler bootstrap std
cli check format lsp test verify bench release vscode
```

A group milestone normally uses one `mini-v*` release tag. Product tags are used
when a product needs its own release or diagnostic build. Do not create one
release per internal increment unless that release is intended to be published.

GitHub limits individual tag-push workflow events. Push at most three new tags
at a time.

## Historical tags

Tags created before the release workflow are source milestones, not retroactive
builds. Re-pushing an old tag does not create a build for its original workflow
unless the tag is newly pushed again.

The [progress page](progress.md) records the tag timeline and distinguishes tags
from built releases. Historical tags should not be rewritten just to obtain
builds; create a new milestone release instead.

## Bootstrap requirement

Compiler, language, mini, and bootstrap releases require a verified fixed point.
The workflow bootstraps before checks and again inside the extracted source
archive. Tool-only releases use the same bootstrap but do not claim a new
compiler identity.
